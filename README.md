# 💪 FitLog

> 운동 계획부터 기록, 데이터 분석, AI 상담까지 제공하는 개인 맞춤형 웨이트 트레이닝 플랫폼

**FitLog**는 운동 계획을 수립하고 운동 기록을 관리하며, 누적된 데이터를 기반으로 운동 분석과 AI 상담을 제공하는 개인 맞춤형 웨이트 트레이닝 서비스입니다.

사용자는 운동 루틴을 계획하고 운동 기록을 저장할 수 있으며, 기록된 데이터를 분석하여 자신의 운동 현황을 확인하고 AI 상담을 통해 운동에 대한 피드백을 받을 수 있습니다.

---

# 🎯 프로젝트 목표

FitLog는 운동 계획, 기록, 데이터 분석, AI 상담 기능을 하나의 서비스에서 제공하여 사용자의 체계적인 운동 습관 형성을 지원하는 것을 목표로 개발되었습니다.

또한 운동 기록이 지속적으로 누적되는 환경에서도 안정적인 서비스를 제공하기 위해 대용량 데이터를 가정한 부하 테스트를 수행하고, 조회 성능과 네트워크 전송 구간을 중심으로 최적화를 진행했습니다.

# ⚡ 성능 최적화

## 최적화 배경

5,000명의 활성 사용자가 1년간 매일 20개의 운동 세트를 기록하는 **약 3,650만 건의 데이터 환경**을 가정하여 부하 테스트를 수행했습니다.

테스트 결과 **조회 쿼리와 네트워크 전송 구간이 주요 병목**으로 확인되어 성능 최적화를 진행했습니다.

# 📈 쿼리 최적화

## 성과

| 항목 | 개선 전 | 개선 후 | 개선 효과 |
|------|---------:|---------:|-----------:|
| 평균 응답 속도 | 3,290ms | 133.6ms | **96% 개선** |
| 하위 5% 응답 시간 | 6,910ms | 334.5ms | **95% 개선** |
| 시스템 처리량 | 6.2 req/s | 20.4 req/s | **3.3배 향상** |
| 500ms 이내 응답 비율 | 11% | 99% | **9배 향상** |

### 1. 조인 전략 최적화

#### 문제

N+1 문제를 개선하는 과정에서 복잡한 조인으로 인해 조회 성능이 저하되었습니다.

#### 해결

- 커버링 인덱스를 활용하여 식별자와 필요한 컬럼만 우선 조회
- 조회된 ID 목록을 기반으로 `IN` 절을 이용한 연관 데이터 분리 조회

#### 결과

복잡한 다중 조인을 제거하여 조회 성능을 개선했습니다.

---

### 2. 불필요한 Count Query 제거

#### 문제

무한 스크롤 UI 환경에서도 매 요청마다 Count Query가 수행되고 있었습니다.

#### 해결

전체 개수를 사용하지 않는 화면임을 확인한 후 `Page` 대신 `Slice`를 사용하여 Count Query를 제거했습니다.

#### 결과

불필요한 데이터베이스 연산을 제거하여 응답 속도를 개선했습니다.

---

### 3. 집계 연산 최적화

#### 문제

문자열 합산 및 복잡한 집계 연산을 데이터베이스에서 수행하여 병목이 발생했습니다.

#### 해결

집계 및 가공 로직을 Java 애플리케이션 계층으로 이전하여 메모리 기반으로 처리했습니다.

#### 결과

데이터베이스 부하를 감소시키고 처리 속도를 향상시켰습니다.

# 🌐 네트워크 최적화

## 성과

| 항목 | 개선 전 | 개선 후 | 개선 효과 |
|------|---------:|---------:|-----------:|
| 데이터 수신량 | 3.8MB | 850KB | **78% 감소** |
| 평균 응답 시간 | 57.11ms | 33.58ms | **41% 개선** |
| 네트워크 수신 속도 | 722.23μs | 122.57μs | **83% 개선** |
| 하위 5% 응답 시간 | 90.56ms | 54.43ms | **40% 개선** |

### 1. HTTP/2 적용

#### 문제

HTTP/1.1 환경에서 다수의 리소스를 요청할 경우 요청 대기로 인해 병목이 발생했습니다.

#### 해결

Nginx에 HTTP/2를 적용하여 멀티플렉싱을 통한 리소스 전송 효율을 개선했습니다.

---

### 2. ETag 기반 브라우저 캐시 적용

#### 문제

사용자가 동일한 데이터를 반복 조회하면서 불필요한 데이터 전송과 DB 조회가 발생했습니다.

#### 해결

데이터의 마지막 수정 시각을 기반으로 ETag를 생성하여 변경 사항이 없는 경우 304(Not Modified)를 반환하도록 구현했습니다.

#### 결과

중복 데이터 전송을 방지하고 서버 자원을 절약했습니다.

---

### 3. Gzip 압축 적용

#### 문제

JSON 기반 응답 데이터의 크기가 증가하면서 네트워크 전송 비용이 커졌습니다.

#### 해결

Gzip 압축을 적용하여 응답 데이터를 압축한 후 전송하도록 구성했습니다.

#### 결과

전송 데이터 크기를 줄이고 사용자 응답 속도를 개선했습니다.
